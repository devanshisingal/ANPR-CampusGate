PART 1 - PROJECT OVERVIEW AND PROBLEM STATEMENT
================================================================================

1.1 What ANPR-CampusGate Is
---------------------------
ANPR-CampusGate (repository: ANPR-RM) is an end-to-end Automatic Number Plate
Recognition (ANPR / ALPR) and campus gate vehicle-intelligence system tailored
for Indian license plates. It ingests prerecorded gate videos or RTSP camera
streams, detects and tracks vehicles across consecutive frames, localizes
license plates, extracts and normalizes Indian registration strings using CPU-
accelerated ONNX/RapidOCR engines (with optional TensorRT/GPU backends), detects
gate movement direction (IN vs OUT vs UNKNOWN), enforces pre-storage blacklist
security alerting and whitelist classification, attributes vehicle color and
type, maintains longitudinal multi-camera vehicle trajectories, and surfaces live
telemetry, video previews, alerts, and historical analytics via a FastAPI REST/
MJPEG backend and multiple web dashboards (Next.js 15 primary UI and Streamlit).

1.2 The Problem Being Solved
----------------------------
University and institutional campuses experience dense mixed traffic across two-
wheelers, three-wheelers, hatchbacks, sedans, SUVs, buses, and utility trucks.
Campus gate security requires:
  (a) Sub-second flagging of unauthorized, banned, or watchlisted vehicles
      before the vehicle clears the barrier arm;
  (b) Reliable logging of IN/OUT direction and timestamps across multiple gates;
  (c) Automated reconciliation between recurring authorized campus vehicles
      (faculty, staff, registered students, service vans) and ad-hoc visitors;
  (d) Resilience to real-world Indian license plate diversity: HSRP two-line vs
      single-line plates, regional fonts, perspective skew, motion blur, glare,
      dust, partially occluded frames, and ambiguous lookalike characters
      (0/O/D/Q, 1/I/L/T, 2/Z, 5/S, 8/B, 6/G).

1.3 Why Manual Gate Monitoring and Basic Single-Frame Detectors Fail
--------------------------------------------------------------------
Manual register logging at peak campus hours causes gate queues, high error
rates in illegible handwriting, zero cross-gate correlation, and no automated
blacklist alerting. Conversely, naive "upload image -> run OCR" detectors fail
in continuous video streams because:
  1. Single-frame OCR suffers high character-substitution errors when a plate is
     small (<25 px tall), oblique, or blurred by motion.
  2. Processing every frame of every tracked vehicle wastes CPU cycles after a
     confident plate consensus has already been obtained.
  3. Waiting for multi-frame consensus before checking the blacklist adds
     200 ms to >1,100 ms of unnecessary alert delay when a known threat enters.
  4. Without track-aware deduplication and spatial normalization, a single slow
     vehicle creates dozens of duplicate DB entries and triggers repeated alarms.

1.4 Project Objectives
----------------------
1. Deliver an accurate, modular two-stage detection + multi-frame OCR pipeline
   calibrated to Indian state codes and RTO syntax (`^[A-Z]{2}[0-9]{1,2}[A-Z]{0,3}[0-9]{1,4}$`).
2. Achieve interactive near-real-time execution (~16-24 FPS depending on scene
   density) on commodity x86_64 CPUs via ONNX Runtime, while preserving optional
   CUDA / TensorRT execution paths (`yolov8n.engine`, `best.engine`, `parseq_official_tiny.engine`) for NVIDIA Jetson edge nodes.
3. Implement pre-storage blacklist detection directly in the hot video loop so
   watchlisted vehicles raise critical alerts immediately upon high-confidence
   read, ahead of full consensus commit.
4. Provide unified per-vehicle profiling (`VehicleProfile`) linking plate
   events across gates (`camera_id`, GPS `latitude`/`longitude`) into replayable
   movement histories.
5. Support unattended multi-camera monitoring (`CameraManager`) with live
   MJPEG / snapshot streaming, additive DB migration, and browser-based gate
   control via Next.js 15 + FastAPI.

1.7 What Distinguishes ANPR-CampusGate from a Basic Plate Detector
------------------------------------------------------------------
1. Temporal Multi-Frame Consensus (`OCRFusion`): Buffers per-track candidate
   strings, weights votes by `confidence * quality_score`, boosts consensus on
   syntax-valid reads, and performs fallback majority voting only when needed.
2. Pre-Storage Zero-Latency Blacklist Interception: Fires `BLACKLISTED` alert
   the instant an individual OCR read matches `blacklist.yaml` above alert
   confidence threshold, bypassing the consensus delay (~188 ms to 1,127 ms
   measured lead time ahead of final DB storage).
3. Position-Aware Indian RTO Syntax Repair (`ocr_postprocessor.py`): Repairs
   digits in letter slots (`0->O`, `1->I`, `8->B`) and letters in digit slots
   (`O->0`, `I->1`, `B->8`, `S->5`, `Z->2`) plus Levenshtein <= 1 recovery.
4. Early Track Lock-Out (`stored_tracks`): Once a track reaches consensus and
   is persisted, `stored_tracks.add(tid)` suppresses subsequent plate YOLO +
   OCR calls on the same physical vehicle across its remaining exit frames.
5. Multi-Gate Trajectory Memory (`VehicleProfile` + `TrajectoryEngine`): Tracks
   up to 500 JSON camera visits per plate, calculates Haversine distances,
   snaps gate transitions onto campus coordinates, and answers natural-language
   spatial queries (`nl_query.py`).

1.8 End-to-End User Journey
---------------------------
1. User opens Next.js dashboard (`http://localhost:3000`, talking to FastAPI
   `http://localhost:8000`).
2. User either activates configured campus camera streams (`CAM001` Main Gate,
   `CAM002` Back Gate) or uploads a gate MP4 via the upload widget (`POST /api/upload`).
3. `CameraManager` queues uploaded jobs sequentially (or launches camera
   workers), invokes `run_pipeline.py` under shared pipeline inference locking,
   and publishes 8 FPS JPEG previews (`data/live_frames/{camera_id}.jpg`) and
   real-time progress (`data/processing_status.json`).
4. As vehicles enter the frame, ByteTrack assigns consistent IDs (`tid`),
   YOLOv8n crops the license plate, RapidOCR reads the characters, Indian syntax
   repair normalizes the string, and `BlacklistManager` immediately surfaces any
   red alert on the top-bar notification drawer (`GET /api/alerts`).
5. Once `OCRFusion` reaches consensus and `DuplicateFilter` confirms novelty
   within the 30-second window, `ALPRDatabase.insert_event()` records a 22-column
   `VehicleEvent` and atomically updates the 25-column `VehicleProfile` under
   SQLite WAL isolation.
6. The officer searches/filters recent events, inspects the saved vehicle &
   plate thumbnails (`/api/images/...`), views per-vehicle camera trajectories
   on the campus map tab, adds/removes blacklist plates, or exports filtered CSV.

-----------------------------------------------------------

  verified 1,973-image validation split; deployed YOLOv8n (`best_finetuned`)
  reached `mAP50 = 0.9697` / `0.9783` (49 epochs, 3.14M params).
- 404 non-socket unit tests, 160 non-socket integration DB/pipeline tests,
  25 FastAPI ASGI endpoint tests, 35 host socket/probe tests, and a 375-frame
  E2E video smoke test verified passing.
- All 41 backend routes, atomic status persistence, WAL SQLite migration, and
  Next.js 15 hydration/scaling fixes operate cleanly.

CURRENT LIMITATIONS & UNVERIFIED CLAIMS:

- The "833-image fine-tuning dataset" zip and executed Kaggle `.ipynb` cell

- Simultaneous 5-minute dual-RTSP campus camera validation was NOT executed in

2.2 Detailed Component Breakdown (Layers, Files, Classes, I/O, Fallbacks)
-------------------------------------------------------------------------

1) VIDEO INPUT & FRAME CAPTURE
   - Purpose     : Open RTSP streams, webcams, or uploaded MP4/AVI files with
                   automatic reconnection and frame throttling.
   - Codebase    : `src/pipeline/frame_capture.py` -> `FrameCapture`; source URI
                   normalization in `src/utils/video_sources.py` (`is_live_source`,
                   `open_video_capture`, `probe_video_source`).
   - Input       : Video file path, integer webcam index, or RTSP/HTTP URL plus
                   `config['camera']` (`frame_skip`, `resize_width/height`).
   - Output      : `(ret, frame_idx, timestamp_sec, bgr_ndarray)`.
   - Algorithm   : `cv2.VideoCapture` with configurable FFMPEG/OpenCV properties,
                   integer step skipping (`frame_skip`), and exponential RTSP
                   reconnect backoff (`retry_delay`, `max_retries`).
   - Next Stage  : Feeds raw BGR frame into optional `MotionFilter` and
                   `VehicleDetector`.
   - Error/Fallback: On RTSP read drop, attempts timed reconnect; on file EOF,
                   signals clean completion so `OCRFusion.flush_all()` can run.

2) MOTION FILTER (OPTIONAL GATE)
   - Purpose     : Skip redundant empty frames when scene is completely static.
   - Codebase    : `src/pipeline/motion_filter.py` -> `MotionFilter` (plus inline
                   checks in `scripts/run_pipeline.py`).
   - Input       : Consecutive BGR frames.
   - Output      : Boolean (`has_motion`), changed foreground pixel ratio.
   - Algorithm   : OpenCV `cv2.createBackgroundSubtractorMOG2` foreground mask
                   area thresholded against `min_motion_area`.
   - Status      : Implemented and unit-tested; note `config.yaml` allows running
                   with continuous tracking when active traffic is processed.

3) VEHICLE DETECTION
   - Purpose     : Detect bounding boxes and coarse classes of road vehicles.
   - Codebase    : `src/detection/vehicle_detector.py` -> `VehicleDetector`; shared
                   ONNX wrapper `src/detection/_onnx_yolo.py` -> `OnnxYoloDetector`.
   - Input       : Full BGR video frame.
   - Output      : List of dicts: `{bbox: [x1,y1,x2,y2], confidence, class_id, class_name}`.
   - Algorithm   : `models/vehicle_detector/yolov8n.onnx` via ONNX Runtime CPU
                   ExecutionProvider (`imgsz=480`, `conf=0.5`, `iou=0.45`). Filters
                   COCO classes `{2: car, 3: motorcycle, 5: bus, 7: truck}`
                   (mapped in classifier/detector).
   - Fallback    : Supports `.pt` (Ultralytics PyTorch) or `.engine` (TensorRT) if
                   configured; `_onnx_yolo.py` dynamically inspects input shape and
                   applies letterbox preprocessing + NMS postprocessing.

4) OBJECT TRACKING
   - Purpose     : Maintain consistent integer `track_id` (`tid`) per vehicle
                   across frames to enable fusion, direction calculation, and skip-lock.
   - Codebase    : `src/tracking/vehicle_tracker.py` -> `VehicleTracker`.
   - Input       : Frame vehicle detections + frame dimensions.
   - Output      : Tracked detections annotated with stable `track_id`.
   - Algorithm   : Uses `supervision.ByteTrack` (Kalman filter state estimation +
                   two-stage high/low confidence Hungarian assignment).
   - Fallback    : Built-in greedy IOU tracker activates automatically if
                   `supervision` fails or is unavailable.

5) LICENSE PLATE DETECTION
   - Purpose     : Localize license plate bounding boxes inside either each
                   active tracked vehicle ROI or full-frame fallback.
   - Codebase    : `src/detection/plate_detector.py` -> `PlateDetector` using
                   `src/detection/_onnx_yolo.py`.
   - Input       : Vehicle crop (padded ROI) when vehicle track present; skips
                   tracks already in `stored_tracks`.
   - Output      : Plate bbox in global frame coordinates + cropped plate BGR
                   array + detector confidence (`>= 0.28`).
   - Algorithm   : Active model is `models/plate_detector/best_finetuned.onnx`
                   (YOLOv8n architecture, `3,138,003` params, `imgsz=320`).
   - Fallback    : Expands vehicle ROI margin slightly; if ONNX session fails,
                   falls back safely without crashing the frame loop.

6) IMAGE PREPROCESSING & SUPER-RESOLUTION
   - Purpose     : Prepare cropped plate patches for OCR robustness and compute
                   laplacian blur / contrast quality metrics.
   - Codebase    : `src/ocr/plate_preprocessor.py` -> `PlatePreprocessor` &
                   `src/ocr/super_resolution.py` -> `SuperResolutionEnhancer`.
   - Input       : Raw cropped plate BGR patch.
   - Output      : Preprocessed crop(s) + image `quality_score` (laplacian variance,
                   brightness, aspect ratio).
   - Algorithm   : Grayscale / CLAHE local contrast enhancement, adaptive scaling,
                   optional deskewing. Notice `config.yaml` sets
                   `sr_threshold_px: 0` (disabling SR in active CPU mode because
                   RealESRGAN `x4plus` weights are absent in `models/` and `cv2.dnn_superres`
                   bicubic/ESPCN fallback adds CPU latency).

7) HEAVY-TRACK OCR BUDGET GATE
   - Purpose     : Bound per-frame OCR CPU cost during crowded frames.
   - Codebase    : `scripts/run_pipeline.py` (orchestrator loop).
   - Algorithm   : Caps heavy OCR execution at `heavy_track_max_per_frame = 2`
                   un-stored tracks per frame, prioritizing tracks with fewer
                   prior OCR attempts (`track_ocr_attempts`) and higher plate conf.

8) OPTICAL CHARACTER RECOGNITION (OCR)
   - Purpose     : Convert plate crop pixels into alphanumeric character strings.
   - Codebase    : `src/ocr/ocr_engine.py` (factory + `RapidOCREngine`, `PARSeqTRTEngine`,
                   `EnsembleOCREngine`, `PaddleOCREngine`, `EasyOCREngine`, `TrOCREngine`).
   - Input       : Cropped plate patch (single or multi-variant candidates).
   - Output      : `(raw_text, raw_confidence)` plus two-line stitching if
                   split across top/bottom rows.
   - Algorithm   : Active CPU backend (`ocr.engine: "rapidocr"`) executes
                   `rapidocr_onnxruntime` (PP-OCR ONNX: DBNet text detector with
                   `det_limit_type="max"`, `det_limit_side_len=320`, angle
                   classifier disabled `use_angle_cls=False`, SVTR recognizer).
   - Error/Fallback: Handles empty detections, merges vertical multi-box reads
                   on 2-line Indian plates (motorcycles/commercial plates), and
                   rejects reads with confidence below threshold. Note: PARSeq
                   ONNX (`parseq_official_tiny.onnx`) fails on CPU ORT due to
                   `Where(16)` op and is reserved for TensorRT `.engine` hardware.

9) OCR POST-PROCESSING & INDIAN SYNTAX VALIDATION
   - Purpose     : Normalize character ambiguities and validate RTO structure.
   - Codebase    : `src/ocr/ocr_postprocessor.py` & `src/ocr/plate_validator.py`.
   - Input       : Raw uppercase alphanumeric string.
   - Output      : Cleaned plate string, `is_valid` boolean, confidence adjustment.
   - Algorithm   : Strips punctuation/IND/BH noise, enforces Indian structure
                   `^[A-Z]{2}[0-9]{1,2}[A-Z]{0,3}[0-9]{1,4}$` (plus BH series
                   `[0-9]{2}BH[0-9]{4}[A-Z]{1,2}`), applies position-specific
                   confusion maps (`0<->O`, `1<->I`, `8<->B`, `2<->Z`, `5<->S`),
                   validates 2-letter state prefix against ~36 valid Indian state
                   / UT RTO codes (`MH`, `DL`, `KA`, `UP`, `BR`, `TN`, `GJ`, etc.),
                   and attempts single-edit state prefix recovery.

10) IMMEDIATE PRE-STORE BLACKLIST CHECK (SECURITY FAST-PATH)
    - Purpose    : Alert operators immediately when a blacklisted vehicle is
                   detected without waiting 2-5 frames for temporal consensus.
    - Codebase   : `scripts/run_pipeline.py` calling `src/access_control/blacklist.py`
                   (`BlacklistManager`) right after single-frame OCR validation.
    - Algorithm  : Normalizes plate (`re.sub(r'[^A-Z0-9]', '', s.upper())`),
                   checks YAML-backed set with `os.path.getmtime` auto-reload,
                   computes optional fuzzy similarity, fires critical alert into
                   `alerts` / callbacks when individual confidence meets
                   `ocr.confidence_threshold` (`>= 0.70`). Marks track as
                   pre-alerted so Step 13 fallback alert skips duplicate firing.

11) MULTI-FRAME TEMPORAL FUSION (`OCRFusion`)
    - Purpose    : Aggregate noisy single-frame reads across a vehicle's pass
                   into a high-confidence consensus string.
    - Codebase   : `src/ocr/ocr_fusion.py` -> `OCRFusion`.
    - Input      : Per-frame `(track_id, plate_text, confidence, quality_score)`.
    - Output     : `ConsensusResult(plate, confidence, status, vote_count)` when
                   consensus criteria are satisfied.
    - Algorithm  : Maintains per-track deque (`window_size=5`); scores each
                   candidate with syntax-validity boost; triggers early exit
                   once `early_exit_votes = 3` uncontested reads agree at
                   weighted confidence `>= 0.82`, or resolves on `min_exact_votes = 2`
                   and `min_confidence = 0.60`. At video EOF, `flush_all()`
                   finalizes remaining unstored valid tracks with relaxed
                   thresholds (`>= 2` votes and `>= 0.9 * min_conf = 0.54`).

12) DIRECTION DETECTION
    - Purpose    : Classify vehicle trajectory as `IN`, `OUT`, or `UNKNOWN`.
    - Codebase   : `src/tracking/direction_detector.py` -> `DirectionDetector`.
    - Input      : Sequence of bounding box centers `[cx, cy]` and box heights
                   per `track_id`.
    - Output     : String `"IN" | "OUT" | "UNKNOWN"`.
    - Algorithm  : Supports crossing virtual line (`line_crossing`), entry/exit
                   zones (`zone`), or bounding-box perspective vertical growth /
                   `delta_y` displacement (`auto`/`centroid` displacement) calibrated
                   per camera config (`camera_config.yaml`).

13) DUPLICATE-EVENT PREVENTION (`DuplicateFilter`)
    - Purpose    : Suppress repeated DB rows from flickering tracks or slow cars.
    - Codebase   : `src/tracking/duplicate_filter.py` -> `DuplicateFilter`.
    - Input      : Candidate `(plate_text, track_id, timestamp, camera_id)`.
    - Output     : Boolean `is_duplicate`.
    - Algorithm  : Rejects if identical `track_id` already emitted OR same-length
                   plate within `time_window = 30.0` seconds has Levenshtein
                   distance `<= 2` (`same length` guard prevents merging unrelated
                   short/long plates).

14) VEHICLE ATTRIBUTE & PROFILE CLASSIFICATION
    - Purpose    : Enrich events with vehicle category, body/plate color, and
                   whitelist/blacklist status.
    - Codebase   : `src/classification/vehicle_classifier.py`,
                   `src/classification/vehicle_color.py`,
                   `src/classification/color_classifier.py`,
                   `src/access_control/whitelist.py`.
    - Algorithm  : `VehicleClassifier` maps YOLO class IDs (car/motorcycle/bus/
                   truck) + bbox geometry; `VehicleColorDetector` segments upper/
                   lower HSV histograms in center crop to estimate body color;
                   `ColorClassifier` classifies plate background color (white
                   private, yellow commercial, green EV, black rental, blue/red);
                   `WhitelistManager` resolves `AUTHORIZED` vs `UNKNOWN`.

15) DATABASE PERSISTENCE & TRAJECTORY PROFILING
    - Purpose    : Atomically record finalized events and update multi-gate
                   longitudinal vehicle history.
    - Codebase   : `src/database/models.py`, `src/database/db.py` (`ALPRDatabase`),
                   `src/database/vehicle_profiles.py` (`VehicleProfileManager`).
    - Storage    : SQLite (`data/alpr.db`, WAL mode, 30s busy timeout) or
                   PostgreSQL (`DATABASE_URL`). `insert_event()` commits row in
                   `vehicle_events` (22 cols) and executes nested `SAVEPOINT` to
                   upsert `vehicle_profiles` (25 cols, appending up to 500 JSON
                   visits into `trajectory_history`).

16) REAL-TIME TELEMETRY & LIVE STREAM PUBLISHING
    - Purpose    : Expose live annotated video and job progress to dashboards.
    - Codebase   : `scripts/run_pipeline.py` -> `LiveFramePublisher` and atomic
                   status writers.
    - Output     : Annotated JPEGs written atomically (`mkstemp` + `os.replace`)
                   at max 8 FPS to `data/live_frames/{camera_id}.jpg`, plus
                   `data/processing_status.json` metrics (`fps`, `avg_detection_ms`,
                   `avg_ocr_ms`, frame progress, alerts).

17) BACKEND REST API & CLIENT DASHBOARDS

PART 4 - MODEL ARCHITECTURES AND MATHEMATICAL FORMULATIONS
================================================================================

4.1 YOLOv8 Vehicle & Plate Detectors (`yolov8n.onnx`, `best.pt`, `best_finetuned.onnx`)
---------------------------------------------------------------------------------------
- Backbone (CSPDarknet with C2f + SPPF):
  Replaces YOLOv5's C3 block with `C2f` (Cross-Stage Partial Bottleneck with
  two 3x3 convolutions and multi-branch gradient-flow concatenation), ending in
  Spatial Pyramid Pooling Fast (`SPPF`, three cascaded 5x5 max-pools) for
  multi-scale receptive fields.
- Neck (PAN-FPN):
  Top-down FPN + bottom-up PAN pathway fusing multi-scale feature maps `(P3, P4, P5)`
  at strides `(8, 16, 32)` so tiny distant license plates (e.g., 20-40 px width)
  retain spatial sharpness from P3 while preserving vehicle context from P5.
- Head (Decoupled Anchor-Free Split Head):
  Separates classification and box regression into independent convolutional
  branches predicting bounding box offsets `(l, t, r, b)` from anchor points via
  softmax distribution bins (`reg_max = 16`).
- Parameter / Compute Comparison Across Project Models:
  * Vehicle `yolov8n.onnx` (COCO-80, `imgsz=480`) : ~3.2M params, 12.78 MB ONNX
  * Plate `best_finetuned.onnx` (YOLOv8n 1-cls, `imgsz=320`): 3,138,003 params,
    ~8.7 GFLOPs, 12.88 MB ONNX (ACTIVE on CPU; `.pt` = 6.49 MB)
  * Plate `best.onnx` (`train-3` YOLOv8s 1-cls, `imgsz=320`): 11,135,987 params,
    28.6 GFLOPs, 44.62 MB ONNX (`.pt` = 22.53 MB, TRT `.engine` = 25.54 MB)
  * Plate Legacy `train/` (YOLOv8m 1-cls, `imgsz=640`): 25,840,339 params,
    78.7 GFLOPs (PyTorch `best.pt` retired)

- YOLOv8 Loss Formulation:
    L_total = lambda_box * L_CIoU + lambda_cls * L_BCE + lambda_dfl * L_DFL
  where:
    * L_BCE: Binary Cross-Entropy with logits over predicted vs target class score.
    * L_CIoU (Complete IoU loss):
        L_CIoU = 1 - IoU + rho^2(b, b_gt) / c^2 + alpha * v
      where rho^2(b, b_gt) is squared Euclidean center distance, c is diagonal
      of smallest enclosing box, v = (4 / pi^2) * (arctan(w_gt/h_gt) - arctan(w/h))^2
      enforces aspect-ratio consistency critical for rectangular plates.
    * L_DFL (Distribution Focal Loss):
        DFL(S_i, S_{i+1}) = -((y_{i+1} - y)*log(S_i) + (y - y_i)*log(S_{i+1}))
      shapes the discrete 16-bin distribution around continuous ground-truth
      box edges.

4.2 Object Tracking (`VehicleTracker`: ByteTrack + Kalman + Hungarian)
----------------------------------------------------------------------
- State Vector: `x = [u, v, s, r, du, dv, ds]^T` (center `(u,v)`, scale `s`,
  aspect ratio `r`, and velocities). Constant-velocity Kalman predict/update
  propagates boxes across occluded frames (`lost_track_buffer`).
- Two-Stage Association (ByteTrack):
  1. High-confidence detections (`>= track_thresh`) matched to existing tracks via
     IoU cost matrix + Jonker-Volgenant (`lap`/Hungarian) assignment.
  2. Remaining unmatched tracks matched against low-confidence detections so
     momentarily blurred/occluded vehicles keep continuous IDs (`tid`).
- Fallback Mode: If `supervision.ByteTrack` raises import/runtime issues,
  reverts to greedy frame-to-frame IoU bipartite association.

4.3 Optical Character Recognition Engines
-----------------------------------------
(A) ACTIVE CPU ENGINE — RapidOCR (`rapidocr_onnxruntime`):
  Three-stage decoupled ONNX pipeline (with `use_angle_cls=False` enabled for speed):
  1. Text Detection (`DBNet` - Differentiable Binarization): MobileNetV3/ResNet
     backbone predicts probability map P and adaptive threshold map T;
     approximate step function B_hat = 1 / (1 + exp(-k*(P - T))) isolates sharp
     plate polygon boxes at `det_limit_side_len=320` (`det_limit_type="max"`).
  2. Direction Classifier (DISABLED): `cls=False` eliminates redundant 180-deg
     orientation classification overhead on upright campus CCTV plates.
  3. Text Recognition (`SVTR` / CRNN CTC head): Extracts fixed-height strip
     features and decodes variable-length character logits via CTC greedy search.

(B) EXPERIMENTAL / JETSON EDGE ENGINE — PARSeq (`baudm/parseq-tiny` & legacy CNN):
  1. Image Encoder: Vision Transformer (`ViT`) splits plate crop `(32 x 128)` into
     patches (`4 x 8` patch tokens) with positional embeddings.
  2. Permutation Language Modeling (PLM) Autoregressive/Iterative Decoder:
     Cross-attention decoder masks token positions under randomized permutations
     during training so at inference it supports both left-to-right decoding and
     iterative context refinement of ambiguous characters without CTC independence
     assumptions.
  3. Status in Repo: Official `parseq_finetune_lightning_best.ckpt` (`baudm/parseq-tiny`)
     exports cleanly to `parseq_official_tiny.onnx` (24.26 MB) and NVIDIA TensorRT
     `parseq_official_tiny.engine` (16.46 MB), HOWEVER `parseq_official_tiny.onnx`
     cannot run on CPU `onnxruntime` due to `NotImplemented: Where(16)` operator
     constraint, making RapidOCR mandatory on Windows x86 CPU.

4.4 Validation, Syntax Repair & Multi-Frame Fusion Mathematics
--------------------------------------------------------------
- Regular Expressions (`PlateValidator`):
    Standard Indian RTO : `^[A-Z]{2}[0-9]{1,2}[A-Z]{0,3}[0-9]{1,4}$`
    Bharat (BH) Series  : `^[0-9]{2}BH[0-9]{4}[A-Z]{1,2}$`
- Levenshtein Edit Distance (`D(a, b)`):
  Dynamic programming cost counting single-character insertions, deletions, and
  substitutions. Used in:
  * `DuplicateFilter`: Duplicate if `len(a) == len(b)` AND `D(a, b) <= 2` within `30s`.
  * `ocr_postprocessor`: State-prefix nearest neighbor lookup within edit distance 1.
- Weighted Multi-Frame Fusion Score (`OCRFusion`):
    frame_weight(r) = r.confidence * (0.6 + 0.4 * r.quality_score) * valid_bonus
  - Validated per-frame reads feed fusion; consensus fires on `early_exit_votes=3`
    uncontested @ `>= 0.82` OR at buffer window (`5`) on `min_exact_votes=2` and
    weighted mean confidence `>= min_confidence (0.60)`.

4.5 Spatial Trajectory & Color Mathematical Formulations
--------------------------------------------------------
- Haversine Inter-Camera Distance (`TrajectoryEngine`):
    a = sin^2(dlat/2) + cos(lat1) * cos(lat2) * sin^2(dlon/2)
    distance_m = 2 * R_earth * atan2(sqrt(a), sqrt(1 - a)),  R_earth = 6,371,000 m
- HSV Vehicle Body Color Segmentation (`VehicleColorDetector`):
  Samples central torso ROI of vehicle bounding box (excluding wheels, glass
  glare via `V` clipping, and plate box) and histograms `(H, S, V)` channels to
  classify into discrete buckets (`white`, `black`, `silver/gray`, `red`, `blue`,
  `green`, `yellow`, etc.).

6.2 Step-by-Step CPU Latency Optimization Engineering (1.25 FPS -> 19.18-23.76 FPS)
-----------------------------------------------------------------------------------
Baseline bottleneck analysis on Ryzen 7 7840HS CPU revealed why initial live runs
crawled at **1.25 FPS** (`plate_det = 101.6 ms/call`, `ocr = 556.5 ms/call`):
  1. Switched PyTorch `.pt` YOLO inference -> ONNX Runtime `.onnx` via custom
     `_onnx_yolo.py` (eliminated PyTorch dynamic graph & Ultralytics Python glue),
     plus moved primary plate model from 11.14M-param YOLOv8s to 3.14M-param
     `best_finetuned.onnx` (`YOLOv8n`) at `imgsz=320`: dropped plate detection from
     `101.6 ms` -> **`13.40 - 15.54 ms`** (~6.8x speedup).
  2. Optimized RapidOCR PP-OCR execution (`det_limit_side_len=736 -> 320` and
     disabled unused `180-deg` angle classifier `use_angle_cls=False`): slashed
     OCR average per call from `556.5 ms` -> **`23.33 - 39.51 ms`** (~14-24x speedup).
  3. Bypassed CPU super-resolution (`sr_threshold_px=0`, skipping bicubic/ESPCN
     upscale overhead when RealESRGAN GPU weights are absent).
  4. Added `stored_tracks.add(tid)` early exit + `heavy_track_max_per_frame = 2`
     budget: eliminated redundant plate YOLO + RapidOCR work on tracks whose plate
     was already finalized.

Net Measured Gains (`logs/alpr.log` + `data/processing_status.json`):
  - Initial CPU Baseline          : **1.25 FPS** (det 101.6 ms, ocr 556.5 ms)
  - Optimization Pass 1 (200f)    : **12.51 FPS** (plate 30.67 ms, ocr 47.24 ms)
  - Optimization Pass 2 (200f)    : **23.76 FPS** rolling peak (plate 13.54 ms, ocr 23.33 ms)
  - Full 1,500-Frame Benchmark    : **19.18 FPS** (`78.20s`, 6/6 vehicles caught)
  - Live `CAM001` UI Session (401f): **16.27 FPS** (plate 15.54 ms, ocr 39.51 ms)

PART 7 - OBJECT TRACKING, DIRECTION DETECTION, FUSION, AND PROFILING
================================================================================

7.1 Multi-Frame Track Lifecycle & Early Exit State Machine
----------------------------------------------------------
1. Initial Detection (`VehicleTracker.update`): ByteTrack links vehicle
   bounding boxes across consecutive frames and emits persistent `track_id` (`tid`).
2. Active OCR Collection (`track_id not in stored_tracks`):
   - Runs `PlateDetector` inside the vehicle ROI (min guard `36x12 px`).
   - Enforces `max_heavy_tracks_per_frame = 2` (files) / `1` (live).
   - Runs `RapidOCREngine` -> `ocr_postprocessor` -> `PlateValidator`.
   - Checks `BlacklistManager` immediately at confidence `>= 0.70` (pre-store).
   - Pushes candidate read `(plate, conf, quality, is_valid)` into `OCRFusion`.
3. Consensus & Commitment (`OCRFusion`):
   - Triggered early when `early_exit_votes = 3` uncontested reads agree at
     weighted confidence `>= 0.82`, or across `window_size = 5` at
     `min_exact_votes = 2` and `min_confidence = 0.60`.
   - Invokes `DuplicateFilter.is_duplicate()`:
     * Blocks same `track_id` OR same-length string within `30.0s` having
       Levenshtein distance `<= 2`.
   - Executes `ALPRDatabase.insert_event()` + atomic `VehicleProfile` update.
   - Calls `stored_tracks.add(tid)` and clears per-track OCR buffer.
4. Locked Track Optimization: Every subsequent frame containing `tid` bypasses
   Plate YOLO, preprocessing, and RapidOCR completely, only continuing cheap
   vehicle bounding-box tracking (for overlay display and exit timing).
5. End-of-Stream Fallback (`ocr_fusion.flush_all`): Any un-stored valid tracks
   still in buffer at EOF finalize with relaxed criteria (`>= 2` exact votes
   and `>= 0.9 * min_confidence = 0.54`).

7.2 Direction Detection Mechanics (`src/tracking/direction_detector.py`)
------------------------------------------------------------------------
- `DirectionDetector` maintains trajectory deque of `[cx, cy, h]` per `track_id`
  and resolves `"IN"`, `"OUT"`, or `"UNKNOWN"` using camera configuration rules:
  1. Line Crossing Mode (`line_crossing`): Evaluates signed cross-product sign
     flip relative to a configured gate virtual line (`x1, y1, x2, y2`).
  2. Zone Transition Mode (`zone`): Detects sequential traversal from entry
     polygon to exit polygon (or vice versa).
  3. Vertical/Perspective Delta Mode: Uses signed centroid shift `(cy_end - cy_start)`
     and bounding-box height expansion (`dh = h_end - h_start`) exceeding pixel
     motion thresholds when explicit line geometry is absent.
- Edge-Case Handling: Stationary parked vehicles near gates return `"UNKNOWN"`
  below displacement threshold rather than guessing `IN`/`OUT`.

7.3 Vehicle Profiling & Multi-Camera Trajectory Linkage
-------------------------------------------------------
- `src/database/vehicle_profiles.py` (`VehicleProfileManager`) transforms flat
  individual gate detections into a longitudinal entity keyed by normalized
  uppercase `plate_number`:
  * Tracks `first_seen`, `last_seen`, `total_detections`, `total_camera_visits`,
    `unique_cameras`, `last_direction`, `status`, `vehicle_type`, `vehicle_color`,
    and `plate_color`.
  * Appends structured visit dictionaries `{camera_id, camera_name, timestamp,
    direction, confidence, latitude, longitude}` into `trajectory_history` JSON
    (capped safely at the most recent **500 visits** to bound SQLite row growth).
  * `TrajectoryEngine` (`src/trajectory/`) builds directional edges between gate
    pairs, calculates inter-camera Haversine distances (`meters`), computes
    median/min transit speeds (`km/h` / time deltas), and powers Leaflet maps,
    GeoJSON exports, spatial heatmaps, and natural-language SQL/JSON queries.

8.2 Architectural Notes: Logical Relationship, SAVEPOINT & Unused DDL
---------------------------------------------------------------------
1. Logical Key Join (No Formal SQL `FOREIGN KEY` Constraint):
   `VehicleEvent` and `VehicleProfile` relate logically through uppercase
   stripped `plate_number`, intentionally omitting hard SQL foreign-key
   constraints so legacy events can be imported out-of-order or purged by session
   without cascading profile corruption.
2. Nested `SAVEPOINT` Synchronization (`src/database/db.py`):
   Inside `insert_event()`, after flushing the `VehicleEvent` row, the DB layer
   opens `session.begin_nested()` (`SAVEPOINT`) to upsert the corresponding
   `VehicleProfile` row. If profile JSON parsing fails unexpectedly, only the
   nested savepoint rolls back while preserving the primary event record.
3. In-Place Additive Migration (`_migrate_schema`):
   Upgrades legacy 8-column `vehicle_events` SQLite tables in-place via 14
   non-destructive `ALTER TABLE ADD COLUMN` statements + 2 index creations,
   catching duplicate-column errors cleanly across concurrent workers.
4. SQLite WAL Mode Concurrency:
   Executes `PRAGMA journal_mode=WAL;`, `PRAGMA synchronous=NORMAL;`, and
   `30s` busy timeout so FastAPI dashboard reads never block behind active
   pipeline video ingestion.
5. CRITICAL CODEBASE FINDING — UNUSED Normalized DDL (`src/database/postgres_schema.py`):
   `postgres_schema.py` contains a full normalized PostgreSQL DDL defining
   **6 tables** (`cameras`, `vehicles`, `entries`, `images`, `logs`,
   `duplicates_detected`) plus **1 materialized view** (`daily_traffic_stats`).
   Trace inspection confirms this file is **NOT wired into the active ORM or API**;
   even when running against PostgreSQL via `DATABASE_URL`, SQLAlchemy creates and
   queries `vehicle_events` and `vehicle_profiles` defined in `models.py`.

9.2 `CameraManager` (`src/cameras/camera_manager.py`): Dual Execution Model
--------------------------------------------------------------------------
`CameraManager` intentionally isolates interactive upload batch jobs from
continuous RTSP camera workers:
  1. Uploaded MP4 Queue (`FIFO Worker Thread`):
     User-uploaded videos enter a sequential FIFO thread queue so competing CPU
     pipeline jobs never thrash all 16 Ryzen threads simultaneously. Each upload
     spawns/executes `scripts/run_pipeline.py` (subprocess/managed runner), writes
     progress atomically to `data/processing_status.json` (`mkstemp` +
     `os.replace`), and tags events with an isolated `processing_session` ID
     (e.g., `"20261111-144304-028d72"` verified in `data/processing_status.json`).
  2. Multi-Camera Live RTSP Workers:
     Supports multiple concurrent `CameraWorker` capture threads reading RTSP
     frames continuously, while synchronizing heavy shared ONNX/YOLO/OCR inference
     passes through a shared **`threading.RLock()`** when operating under single-
     process shared-model mode to guarantee thread safety across ONNX sessions.
  3. Reconnection & Health Monitoring:
     Implements stale-frame detection (comparing `LiveFramePublisher` timestamp
     age), offline/reconnecting states, exponential retry waits, and API hooks
     to start, stop, add, update, probe, or delete cameras dynamically.

13.1 Strict Epistemic Separation of Metrics
-------------------------------------------
In academic presentations and viva examinations, three fundamentally distinct
metrics MUST NOT be conflated:
  1. Object/Plate Localization mAP (`0.9697 - 0.9832 mAP50`): Measures bounding-
     box overlap of plate regions ONLY. It does NOT measure character reading!
  2. Optical Character Recognition Accuracy / CER: Fraction of characters or
     complete plates decoded accurately by RapidOCR/PARSeq against human ground
     truth. UNBENCHMARKED in this repo (see Section 13.4).
  3. End-to-End Video Event Recall & Blacklist Alert Lead Time: Fraction of
     passing vehicles yielding valid DB events and sub-second blacklist alerts.

  `DELETE /api/blacklist/{plate}`, `POST /api/events/clear`, camera CRUD, and
  file uploads) currently expose NO authentication token / RBAC middleware, and
  CORS allows broad local frontend origins. Deployment outside trusted campus
  LAN VLANs requires adding reverse-proxy auth / JWT guards.

14.2 Reliability & Fault Tolerance Mechanisms Implemented
---------------------------------------------------------
- Atomic State & Media Writes: Both `data/processing_status.json` and
  `data/live_frames/{camera_id}.jpg` write via temp file (`tempfile.mkstemp`) +
  `os.replace()` to eliminate partial/corrupt reads on Windows NTFS.
- SQLite Concurrency Hardening: `WAL` journal mode + `30s` busy timeout +
  nested `SAVEPOINT` for profile updates prevents locked-DB crashes during
  simultaneous video processing and Next.js API polling.
- RTSP Stall & Reconnect Guard: `stall_timeout: 10.0s` detects frozen network
  streams cleanly and triggers bounded reconnects (`max_retries: 5`).
- Single-Model ONNX Thread Lock: `CameraManager` guards shared ONNX model
  inference via `threading.RLock()` across concurrent RTSP camera workers.

PART 15 - ENGINEERING CHALLENGES, DEBUGGING CHRONICLES, AND RESOLUTIONS
================================================================================

1. Challenge: 1.25 FPS Unusable CPU Throughput
   - Root Cause: PyTorch `.pt` YOLO calls (101.6 ms) + RapidOCR `DB736` upscaling
     and enabled 180-deg angle classifier (556.5 ms) + redundant OCR on parked/
     already-stored tracks.
   - Resolution: Exported `.onnx` detectors (`_onnx_yolo.py`), adopted lightweight
     YOLOv8n `best_finetuned.onnx`, capped `det_limit_side_len=320`, `use_cls=false`,
     disabled CPU SR (`sr_threshold_px=0`), and added `stored_tracks` +
     `max_heavy_tracks_per_frame=2` -> Achieved **16.27 - 23.76 FPS**.

2. Challenge: `frame_skip=2` Silently Dropping Vehicles
   - Root Cause: Skipping frames doubled inter-frame displacement, causing
     ByteTrack IoU mismatch and restarting `OCRFusion` vote buffers mid-pass.
   - Resolution: Kept `frame_skip=1` + increased `lost_track_timeout=60` and
     lowered `minimum_matching_threshold=0.5`, recovering **6/6 vehicles**.

3. Challenge: Next.js 15 SSR React Hydration Errors & Tiny UI Legibility
   - Root Cause: Browser password/form extensions injecting `fdprocessedid` +
     SSR/client mismatch and small CSS font tokens reported during dashboard testing.
   - Resolution: Applied clean client hydration safeguards and scaled UI font
     hierarchy / paddings in `frontend/`, committed cleanly without breaking API flow.

4. Challenge: PARSeq Official ONNX Incompatible on CPU ORT
   - Root Cause: Exported `parseq_official_tiny.onnx` uses `Where(16)` semantics
     raising `NotImplemented` on x86 `onnxruntime`.
   - Resolution: Routed default CPU backend cleanly to `rapidocr` while retaining
     `parseq_official_tiny.engine` strictly for CUDA/TensorRT 10.16 targets.

5. Challenge: Audit Discovery of Training Data Leakage & Phantom 25,674 Claim
   - Forensic Audit Discovery: Caught `training/dataset_converter.py` aliasing
     `val == train` in legacy `train/` run (`mAP50=0.9949` invalid) and proved
     `4,116` val in documented `25,674` count was a phantom 20% arithmetic duplicate.
